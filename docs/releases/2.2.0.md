**Pulling changes from GitHub no longer stops when both sides changed:** JuTeX merges them, and you resolve any conflict right in the editor.

## Install

- **Arch Linux:** `sudo pacman -U jutex-2.2.0-1-x86_64.pkg.tar.zst`.
- **Other Linux distributions:** `chmod +x JuTeX_2.2.0_amd64.AppImage` and open it.
- **macOS (Apple Silicon, 13 or later):** open `JuTeX_2.2.0_aarch64.dmg` and drag JuTeX to Applications. It isn't signed by Apple, so macOS blocks it the first time: on macOS 15, System Settings → Privacy & Security → «Open Anyway»; on 13 and 14, right-click the app → Open.
- **Windows 11 (x64):** run `JuTeX_2.2.0_x64-setup.exe` (it installs for your user, without administrator rights). It isn't signed: if SmartScreen warns you, «More info» → «Run anyway».

Download from another machine: `gh release download v2.2.0 -R GASDJUGA/jutex`

## What's new since 2.1.0

### On all platforms

- **Merging when pulling changes.** Before, **Pull changes** refused when both your computer and GitHub had new backups. Now JuTeX first backs up what isn't backed up yet, then merges both sides. Changes in different places (or different files) come together on their own.
- **Conflicts in the editor.** When the same lines changed on both sides, the backup panel lists the files in conflict and each conflict shows in the editor as a box with **Keep mine**, **Keep GitHub's** and **Both**; you can also edit the text by hand. Images and files deleted on one side are resolved by choosing a side in the panel. When nothing is left, **Finish merge** saves the result (and uploads it if «Upload after each backup» is on); **Cancel merge** leaves everything as it was before pulling. A merge left halfway is still there when you reopen the project.
- **Change repository.** The GitHub section of the backup panel has **Change repository**: connect another one (by its address, or create a new private one with `gh`) or disconnect it.
- **Duplicated projects** keep their backups but are no longer connected to the original's repository, so they don't upload to it by mistake.

### Linux

- **Typing is faster in long documents.** Keys pressed together (fast typing) no longer queue up: in a 1055-line document, a burst of keys shows in 14 ms (median) in text and 21 ms in a formula, from 59 and 95 ms.
- **On Wayland, keys go straight to the editor** through GTK's own input module instead of waiting for the compositor's. If an input method is in use (IBus, fcitx, a virtual keyboard) or you set `GTK_IM_MODULE`, JuTeX leaves it alone; dead keys and the Compose key still work. `JUTEX_SYSTEM_IM=1` brings back the system's.

## Known issues

- **Linux (WebKitGTK 2.54, NVIDIA):** the line you just typed sometimes flickers for a moment (~0.2 s), and sometimes the top bar too. It's a WebKitGTK 2.54 bug; with WebKitGTK 2.52 it doesn't happen.
- **Linux (WebKitGTK 2.54, NVIDIA):** when coming back to the window, the active line sometimes flickers for a moment (~0.3 s) between the old one and the new one.
- **Linux:** when typing an accent with a dead key (´ + o), WebKitGTK shows a frame without the accent or the letter; if the line is right at the edge of the window, it looks like a short jump.
- **Merging:** a text file that isn't UTF-8 is resolved by choosing a side, like an image.
